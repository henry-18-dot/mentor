# mentor 性能基线

本地优先的工具必须能回答"本地到底多快"。下面的数字由 `python scripts/bench.py` 产出，
同一批材料、同一批问题、固定重复次数，可随时复现。

- 机器：Windows / Python 3.11.9（本机 `D:\CS336` 工作区）
- 材料：`lectures/lecture_01.py`、`lectures/lecture_06.py`、`docs/setup-notes.md`
- 语料规模：3 个源 / **604 个片段** / 1823 个索引词（平均 8.7 token/片段）

## 摘要（2026-10-16 00:0x 复测）

| 环节 | 数字 |
|---|---|
| 摄取 | **0.047 s** |
| 索引构建（冷启动） | **30.2 ms**（峰值内存 1.8 MB） |
| 索引构建（命中缓存） | 0.002 ms |
| 检索（120 次，limit=8） | 中位 **0.2 ms** / p95 0.3 ms / 最慢 0.5 ms |
| 端到端问答（8 次，离线 provider：检索 + 编排组件 + 接地校验 + 存档） | 中位 **16.4 ms** / p95 23.0 ms |

逐条查询与每次问答的产出见 `runs/bench.md`（脚本默认把同一份内容写在那里）。

### 摄取的增长曲线（本轮修掉的 O(n²)）

`line_for_offset()` 原本每次调用都重建整张 `line_map`，而它**按片段调用一次**，
于是摄取退化成 O(n²)。对抗性验证量出来的曲线：

| 行数 | 修复前摄取 | 修复后摄取 | 修复后 ms/片段 |
|---:|---:|---:|---:|
| 1000 | 155 ms | 90 ms | 0.090 |
| 2000 | 376 ms | 118 ms | 0.059 |
| 4000 | **1616 ms** | **208 ms** | 0.052 |
| 8000 | **12914 ms** | **491 ms** | 0.061 |

修复方式：改用 `bisect.bisect_right(line_map, offset, key=lambda e: int(e[0]))` 直接二分，
不再每次重建表（Python 3.10+ 的 `bisect` 支持 `key`）。8000 行从 12.9 秒降到 0.49 秒（**26 倍**），
复杂度回到线性。`tests/test_performance_guard.py::IngestScalingTest` 用 6000 行的绝对预算钉住这个坑
（修复后约 0.35 s，退化成 O(n²) 时约 7 s）。


## 怎么读这些数字

- **离线问答是"十毫秒级"**：本机不需要联网、不需要 GPU，一次提问从检索到界面描述 <30 ms。
  接上真实模型后，瓶颈完全在网络往返与生成，检索这 0.2 ms 可以忽略——所以检索层做得再快也不会是收益点，
  优化应该花在"少发几次请求、少塞无关上下文"上（这正是多轮上下文与槽位机制在做的事）。
- **索引是懒构建 + 按笔记本缓存**：第一次提问付 31 ms，之后每次提问 0 ms；
  材料变更多少个源就只失效相关笔记本的缓存。
- **内存 1.8 MB** 级别的索引意味着"900 万个片段"这种量级才会成为问题；对个人学习材料（几千片段）远远够用。

## 复现方式

```powershell
cd D:\CS336\mentor
python scripts/bench.py                      # 默认材料与问题、每查询 15 次
python scripts/bench.py --repeat 30 --out runs/bench.md
python scripts/bench.py --root D:\CS336 --files "lectures/*.py" "docs/*.md"
```

改检索、改切块、加组件之后重跑一次，把新表贴在这里对比。

## 防回退护栏

`tests/test_performance_guard.py` 用**很宽松**的阈值盯着灾难性退化（例如不小心写成 O(n²)）：

- 604 片段冷建索引 < 5 s；
- 单次检索 < 0.5 s；
- 端到端离线问答 < 5 s；
- **6000 片段摄取 < 2.5 s**（这条真的抓到过一次 O(n²)：修复前约 7 s）。

阈值故意留了两个数量级的余量——机器负载波动不该让测试变红，但"慢到不能用"必须变红。
真正的性能数字以上面的基线表为准。
